## 3. 次に承認する最小単位：限定取消と取消後の販売照合

推奨対象は **隔離環境で新APIが作成したexact SKU・JPY・割引0・manual支払売上の全取消**。部分取消、返金/決済、旧売上移行、Quick、終了API、POS接続は含めない。初回取消はopen sessionのみとする限定案。既存取消はsessionの存在を確認するがopen制限を持たないため、この制限は既存POS全体を置換できる仕様ではない。

固定route案は `POST /v1/sales/void`。入力は `version:1, transactionId, expectedSaleRequestHash, reason:"manual_void"` のみ。元売上IDを必須とし新売上IDや取消台帳を作らない。取消の操作識別は「元売上ID＋全取消」という固定操作とする。任意path/patch/数量/価格/actor/receiptは禁止。自由文理由・部分取消は後続判断。全3架空UIDを同等扱いし、毎回ID Tokenと確認済みメールを検証する。

### 原子性と証拠の更新案

1. sale/lock/全関連movementを読み、信頼済み販売証拠と入力hashを照合。旧証拠、孤立記録、偽取消、未知状態は409照合待ち。記録なしは未成立と返し、将来の販売を自動取消する予約文書を作らない。実行中販売の不存在証明には使わない。
2. 初回はsession open、元SKUの現在数量・revision・集計整合をtransaction内で確認する。現在variantへ再解決せず、元販売の保存SKU座標と数量を戻す。座標廃止・不明数量・不正revisionなら安全拒否。複数行の同SKUは合算し、正本revisionは変更文書ごとに1増加。対象外SKU/metadataは保持する。
3. 元売上の価格・原価snapshotを保持し、session集計・イベント販売数量は元の効果だけを戻す。現在の他売上を消さない。不整合集計を0に丸めて成功にしない（既存取消のMath.maxによるclampとは区別）。販売/手動編集との競合では固定の戻し意図を再計算し、有限再試行する。
4. saleは既存status/voidReason/voidedByEmail/voidedAt形式、lockは元fingerprintを保持しvoided、戻しmovementは既存 `${transactionId}__void__${行番号}` と `reversalOfTransactionId` を維持する。正本・sale・lock・戻しmovement・session・取消証拠を単一Admin transactionでcommitする。細部フィールドは実装時に既存取消とのfixture比較を必須とする。
5. 元 `serverSaleV1` のcanonical request・保存結果・hashを変更しない。version付き取消証拠領域（候補 `serverVoidV1`）に取消意図、元販売への参照、取消前saleの検証可能なsnapshot、期待取消後saleと戻しmovementのhash・保存結果を結ぶ。取消前snapshotは既存saleHashと必ず照合し、取消後状態の単なる逆推測で正当化しない。
6. 販売commit/resultのproofも限定変更する。元販売movementと正規の戻しmovementを分離し、許可外の追加movementを拒否。整合した取消だけが `currentSaleStatus=voided` として照合可能。販売再送は元販売結果を返し、販売状態をcompletedに戻さず追加減算しない。現在のproofはstatusとmovement件数・saleHashを照合しており、取消route追加だけでは成立しない。
7. 同じ取消意図の再送は保存結果、異なる元hash/意図は409。成功済み取消は後からsessionが閉じても照合できる。Adminによる任意改変への暗号署名保証は追加しない。隔離専用Admin境界とクライアント書込禁止が前提。

承認対象ファイル範囲は `isolated/method-b-sales/` 内の取消処理・既存販売proof/HTTP・専用試験と、関連docs/evidenceのみ。既存製品JS、手動API、旧証拠、稼働設定は変更対象外。

## 5. 価格・EC接続・移行条件

実価格の許容範囲、当時価格を受理する履歴、値引き権限/上限、セット/手動/注文割引の順序、非JPY小数・JPY換算・端数配賦は未対応。隔離policyを本番価格表とみなさない。旧キューの金額を現価格へ自動置換しない。価格/通貨対応は別の限定仕様・試験として承認する。

将来のイベント確保は梱包数量の確定・残量確認と結び付け、イベント日付やsession終了だけで自動解放しない。例：実在庫5・確保3ならEC向け2、イベント販売1後は実在庫4・残確保2でEC向け2を維持する。販売と残確保を二重控除しない。取消は有効な確保へ戻せる場合だけ同じ操作で復元し、終了/最終棚卸済みの確保を黙って復活させない。Quick/未送信で不明な残量は安全側に保全する。

EC注文引当はWooCommerce注文IDとの対応・期限/解除・重複通知・取消/返金との順序を別契約にする。Firestoreと外部注文の原子性はこのAPIのtransactionでは保証できない。現在の販売APIに注文/Bridgeを接続せず、POS売上としてEC注文を複製しない。棚卸、制作完了、材料消費、他2アプリのwriterも操作別APIと移行確認が必要。

安全な切替には全writer棚卸、旧端末/SW/全キュー保全、未送信の照合、3アプリの必要操作対応、実UID/IAM/稼働Rules確認、同時切替/停止手順、実機試験と別の配備承認が必要。現状で直接書込だけを禁止すると既存POSが停止するため実環境のRulesは変更しない。障害時に直接書込へ戻す方式も採らない。
